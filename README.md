# Priors

**An agent that will not hire on a promise it has watched being broken.**

Priors is a buyer on Virtuals Protocol ACP. Before hiring anyone it writes down
what it expects to happen, reads back what actually did, and keeps what it
learned in Sibyl Memory. Delete that memory and it makes different decisions
with identical code.

## The problem

Of 75,340 jobs created on ACP, **40,161 never drew a provider response of any
kind.** Not rejected, not negotiated, not argued over. Asked and ignored.

That is the marketplace an agent has to hire in, and every signal it could use
to choose is produced by the agents it is choosing between. Completion counts,
ratings, the evaluator field: all of it is written by the parties with an
interest in how it reads. Reputation in a market of agents is farmable, and
anything farmable eventually is farmed.

What cannot be farmed is what you watched happen yourself. Priors writes down
what it expects before it hires, reads back what actually happened, and lets
that private record override the public one.

## Verify it in 30 seconds

Open [bzdmin.github.io/priors-acp/#try](https://bzdmin.github.io/priors-acp/#try)
and switch memory from INTACT to DELETED. Eighteen recorded observations drop to
zero weight, the response probability returns to the marketplace prior, and the
same request that was refused is created. Drag the clock forward and the evidence
decays until it expires on day five.

That panel runs the gate from `priors/coordination.py` in the browser over the
agent's exported record. It agrees with the Python to ten decimal places at every
point on the decay curve.

To run the real thing, against the real store:

```bash
git clone https://github.com/bzdmin/priors-acp
cd priors-acp
pip install sibyl-memory-client

python -m unittest discover -s tests -t .    # 58 tests, no data, no network
python scripts/fresh_session.py              # memory intact
python scripts/fresh_session.py --empty      # memory deleted
```

The 150 MB scan ships with the repo, gzipped to 15 MB, so both of those run
without asking anyone for anything.

Across 18,360 resolved jobs:

|---|---|---|
| Accuracy | **0.9035** | 0.9000 |
| Brier score *(lower is better)* | **0.0666** | 0.0721 |
| Decisions changed | **187** | 0 |

There is no `if memory_enabled` branch, and deletion is not a mode. Stages 2
and 3 have nothing to recall, so the prediction falls back to the shrunk

Of the 187 decisions memory changed, 126 were right and 61 were wrong:

| Direction | n | memory right | memory wrong |
|---|---|---|---|
| HIRE → DO NOT HIRE | 181 | 122 | 59 |
| DO NOT HIRE → HIRE | 6 | 4 | 2 |
| **Total** | **187** | **126** | **61** |

Almost every override runs one way, blocking a provider whose public record
looked fine. What Priors learned about this marketplace is that the expensive
mistake is trusting the paperwork.

## Why this problem exists

From a scan of 75,340 ACP jobs, blocks 44,429,969 to 50,749,122. Every figure
below is in [`docs/DATA.md`](docs/DATA.md), regenerated by
`scripts/dataset_stats.py` and never hand-edited.

**Verification is self-refereed.** Of 14,644 completed jobs, a genuine
third-party evaluator appears 18 times. 8,659 were evaluated by the client who
created the job, 5,967 had no evaluator, and a provider never evaluated its
own work. Of 7,356 evaluator fee payments, 7,338 went back to the client.

This does not show the work is bad or that anyone is cheating, only that a
mechanism built for independent verification is not being used independently.

**Most jobs die before they start.** Only 24.38% of created jobs are ever
funded, and the two busiest clients account for 55,004 of the 75,340.

**The average hides everything.** Once funded, 79.47% complete, but among
providers with 150+ funded jobs, completion runs from 1.00 down to 0.05.

Taken together: the public record is not evidence of the thing an agent
actually needs to know.

## How it works

```
ACP on Base ──> events ──> features ──> predict ──> HIRE / DO NOT HIRE
                              │             ↑
                              │        recall (Sibyl)
                              ↓             │
                       outcome resolver ────┘
```

Three stages, of which only the first survives deletion:

1. **Shrunk base rate** from public chain history, using Bayesian shrinkage
   toward the 0.7947 market rate, so a provider with 3 jobs is not read like
   one with 300.
2. **Learned rules** recalled from Sibyl, mined as conditional patterns from
   Priors' own earlier failures.
3. **Calibration**, computed and reported but not applied, for the reasons
   below.

**Write ownership is disjoint.** Priors writes decisions and has no method
that can write an episode, while the resolver writes episodes, rules and
calibration and has no method that can write a decision, which is what makes
the journal's ordering into evidence.

**The leakage rule is structural rather than audited.** Each block is
processed in three phases, absorbing attributes, then predicting, then
absorbing outcomes, so a prediction cannot see its own outcome by
construction. There is no check to forget to run.

**Deterministic.** No wall clock, no RNG and no model call on the decision
path, with time always expressed as a block number.

### Rules have a lifecycle

| | |
|---|---|
| learned rules tested | 156, across 51 providers |
| earned continued trust *(graduated to full weight)* | 16 |
| later demoted, stopped working and lost their weight | 23 |
| still on trial | 117 |

A rule starts as a pattern, becomes provisional at half weight, and graduates
only after proving itself over 10 applications. Demoted rules are archived
rather than deleted, so what Priors used to believe stays readable.

### What Priors refuses to act on

Two mechanisms were built, measured against the frozen baseline, and switched
off because the evidence did not support them.

**Calibration correcting the prediction.** Priors runs hot in the 0.30 to 0.40
band, saying 0.35 where 0.14 actually happens. Letting that correction move
predictions flipped 458 decisions and was right on 45% of them, worse than
chance, because a band-wide average is not evidence about an individual job.

**A learned hiring threshold.** Priors tested whether its own record justified
demanding more than 50% confidence before committing, and every bar above 0.5
scored worse, since failed ACP jobs are refunded from escrow and caution costs
more than it saves. This holds under the symmetric accuracy objective tested,
and under a different cost model the answer could differ.

Calibration remains as self-knowledge that Priors reports without acting on.
Rules earned the right to change behaviour, and these did not.

## Live

Priors follows ACP on **Base mainnet**. History and live are one stream, with
the scan replaying first to rebuild provider history and earned rules, then
`priors/chain.py` taking over at the block the scan ended and feeding the same
loop. `run_replay` groups by block and cannot tell the two apart, so there is
no live-mode branch that could drift from the tested path.

```bash
python scripts/live_tail.py --catch-up-only --no-write   # dry run to head
python scripts/live_tail.py                              # follow
```

A writing run has to replay the scan first, since provider counters and earned
rules come from nowhere else, but the journal is append-only, so writing during
that warm-up would record all 18,367 historical decisions a second time. The
writers therefore drop anything at or below the journal's own high-water block.
That default needs no flag, and `--since-block` overrides it. Entity upserts
are keyed writes and stay idempotent either way.

As of block 50,947,141 on 2026-09-06, catching up 197,912 blocks past the
dataset: **938 live decisions, 937 resolved**, including jobs decided as they
landed.

Three properties a source running unattended needs:

- **Reorg safety.** Only blocks 30 confirmations deep are emitted, so a
  decision written against a block that later disappears cannot be unwritten
  from the journal.
- **Completeness.** The same lag guarantees a block's logs are whole before it
  is yielded, since half a block would let the three-phase loop run against a
  partial picture.
- **Restart safety.** An atomic checkpoint records the last fully processed
  block and never rewinds, so a restart does not re-decide jobs already
  journalled.

### Hiring for real

```bash
cd buyer
npm install
npm run hire
```

Separate lines on purpose. Windows PowerShell 5.1 rejects `&&` with
`The token '&&' is not a valid statement separator in this version`, and `cd`
from anywhere but the repo root gives `Missing script: "hire"`.

**This one needs credentials and will not run for you.** `buyer/.env` holds the
signer for a funded wallet and is not in this repo, so `npm run hire` is here to
show what the buyer does, not as something to reproduce. Everything else on this
page runs without it.

`buyer/src/hire.ts` contains no predictor, shelling out to `scripts/decide.py`,
which runs the same `predict` the backtest and the live tail call. It will not
create a job unless that returns HIRE. The wallet is not constructed until
after the decision.

`evaluatorAddress` is omitted, which puts the job in skip-evaluation mode, so
**Priors does not appoint itself evaluator.** Its own scan found the client
acting as its own evaluator on 8,659 of 14,644 completed jobs. The
`evaluator=0x0000…0000` in the log below is that choice, confirmed on-chain.

The outcome needs no special handling. Once the job is on-chain it appears in
ACP's logs like any other, and `live_tail.py` decodes it, decides on it, and
lets the resolver write the episode through the same path as every other job.

Gas is sponsored by Virtuals' paymaster on Base, so the wallet needs USDC for
the job amount and no ETH.

**This has been executed.** On 2026-09-06 Priors predicted, hired, funded and
paid two jobs on Base mainnet, 0.01 USDC each:


## Coordination: asking before creating

Rules-v2 answers one question, whether a funded job will complete, which leaves
the marketplace's largest failure untouched. Of 75,340 created jobs, only
35,179 ever reached a `BudgetSet` event and only 18,367 were ever funded, so
**53.31% of created jobs never reach a provider response at all.**

`BudgetSet` is the provider-side response step in the ACP SDK. The event
carries no setter address, so these figures are a response rate and are not
presented as a provider acceptance or silence rate.

Priors therefore asks first, and weighs the answer by what it remembers:

```
Priors      writes a request              request row, Priors-owned
Digest      answers that reference        declaration row, counterparty-owned
Resolver    records what followed         observation, resolver-owned
Priors      recalls, then decides
```

Three handles separated by the API rather than by convention. The
counterparty's handle has exactly one method, `declare`, and cannot write a
decision, an observation, or the record that scores its own claims.

```
proceed  =  p_complete >= 0.5      Rules-v2, untouched
        AND p_respond  >= 0.4669   learned, from declaration history
```

The bar is the marketplace prior itself, so an unknown counterparty is treated
as typical rather than as suspect, and an empty store falls back to passing for
the same reason. Reliability shrinks toward that prior, so one broken promise
against one kept promise is not yet evidence. A broken promise halves in weight
each day and is dropped entirely after five, because the gate stops Priors
creating jobs for a blocked counterparty and only a job can produce the
observation that would clear it. Without expiry a blocked counterparty could
never recover.

Coordination can only decline a job Rules-v2 approved, and cannot promote one
Rules-v2 refused.

### The gate cannot measure what it refuses to touch

The gate stops Priors creating jobs for a counterparty it has blocked, and only
a job produces an observation, so evidence about a blocked counterparty cannot
be gathered through the gate that blocks it.

This is not a gap in the implementation. Operating strictly through the gate,
reliability can never fall far below the bar, because it only falls while jobs
keep being created and jobs stop being created exactly when it falls. Starting
from an unknown counterparty that breaks every promise, the gate shuts after
one observation at 0.3891. Interleaving kept promises to hold it open keeps the
ratio pinned at the bar by construction: staying open requires the kept share
to stay above 0.4669, and at 40 observations reliability is still 0.4741, on
the wrong side.

```
observations   kept needed to stay open   reliability
          10                          5        0.4890
          15                          8        0.5167
          40                         19        0.4741
```

This is the selective labels problem. Outcomes are only observable for the
decisions actually taken, which is the same reason a lender cannot tell how the
applicants it rejected would have repaid. Measuring how unreliable a
counterparty really is requires transacting past the point where it is rational
to stop.

So the collection runs behind the figures below were made with the response
gate bypassed, using the `--no-memory` path in `coordinate.py` that the
deletion condition already uses. The observations are unaffected: each one
records what the counterparty did after declaring itself available, and the
request, the declaration and the resolver's write all run normally. What is
bypassed is Priors' own refusal to keep asking. The verdict reported afterwards
uses the full record.

This was not a theoretical concern. The collection run for the figures below
stalled on its very first job, before a single fault had been injected, because
the gate read 0.4587 from four-day-old memory of two broken promises and
declined to create anything:

```
its record      : 3 observed of 6 declared
will it respond : 0.4587 vs bar 0.4669 -> FAIL
coordination declined a job Rules-v2 approved - no job created, nothing spent
```

Once a counterparty carries any adverse record there is no clean first hire
either, so every collection hire bypasses, not only the ones meant to fail.
`scripts/rerun_coordination.py` is the harness that does it.

## What broke, and what each break taught

Running this against a live chain with a counterparty that lies produced eight
distinct failures. Every one of them is fixed, and the fixes are in the commit
history.

| What broke | Why | What it changed |
|---|---|---|
| **Nothing expires an unanswered job** | `JobExpired` needs someone to send a transaction and nobody does. Only 3,112 of the 40,161 jobs that never reached `BudgetSet` emitted one, about 8% | The observer waited forever for a funeral that never happens, so a broken promise could never be recorded. It reads `expired_at` against block time now, which needs no one's cooperation |
| **The gate blocked its own evidence** | After one kept and two broken promises reliability sits below the bar, so no further job can be created, and only a job produces an observation | The collection harness bypasses the gate, and the limitation is written up above as the selective labels problem instead of hidden |
| **Killing an agent leaves orphans** | `npm start` spawns a `tsx` child that survives the wrapper | Four Digest instances accumulated, and two of them accepting one job produced a double `BudgetSet` on job 76935. The harness kills the process tree |
| **A duplicate job on a restart** | The SDK rebuilds sessions for in-flight jobs, so creating another piles a second on top | A guard that resumes instead of creating. This is the bug that guard exists for |
| **The guard then blocked everything** | `JobSession.status` reads the event log, so a job nobody answered stays `open` forever | One unanswered counterparty would have blocked every future job permanently. A job past its own `expired_at` is treated as dead |
| **A faulted hire never exits** | `hire.ts` stops on completed, rejected or expired, and a job nobody answers emits none of them | The harness takes the job id and stops the buyer, since the job is already on chain and silence is the point |
| **The RPC user agent was 403ed** | The string `priors/1.0` is filtered by every public Base endpoint | A clean clone would have got `403 Forbidden` and nothing else. Fixed, along with a chunk size that draws `413 Payload Too Large` |
| **Two fallback endpoints do not serve `eth_getLogs`** | They answer `eth_blockNumber` happily, so they looked healthy | An endpoint answering one method says nothing about another. The list is now only what was probed with the method it is used for |

Two of these are worth reading twice.

**The gate blocked its own script**, before any fault had been injected, on
four-day-old memory of two broken promises:

```
its record      : 3 observed of 6 declared
will it respond : 0.4587 vs bar 0.4669 -> FAIL
coordination declined a job Rules-v2 approved - no job created, nothing spent
```

**The duplicate-job guard and the deadline fix are opposites of each other**, and
both are needed. Too eager and one dead job blocks the agent forever; too lax and
a restart pays twice.

## Sibyl usage

Five primitives, each doing work the product depends on.

| Primitive | What it carries here |
|---|---|
| **Entities (WARM)** | Provider records, the rules currently believed, the calibration ledger. Keyed reads scoped to the subject of a decision. |
| **Journal events (COLD)** | The append-only decision trail, in write order. This is what makes the ordering between a prediction and its outcome checkable. |
| **Archive** | Rules that were demoted. Archived rather than deleted, so what Priors used to believe survives losing its weight. |
| **Search (FTS5)** | Pulling one job's decision and episode out of 36,724 events without a scan, which is what `show_memory.py` prints. |
| **Cursor paging** | `read_events` clamps any limit to 10,000; `iter_journal()` pages past it on the `until` cursor to read the whole journal. |

HOT and REFERENCE are unused. The store is a local file the agent owns.

Current store: **36,724 journal events**, **439 entities** (271 providers, 156
rules, 5 declarations, 5 requests, 1 response record, 1 calibration ledger),
~80 MB on an uncapped account. The eleven declaration, request and response
rows are the coordination layer's own writes.

`read_events` clamps any limit to 10,000 and returns the most recent page, a
deliberate control since SQLite reads a negative `LIMIT` as unbounded.
`PriorsMemory.iter_journal()` pages past it using the `until` cursor the same
method exposes, reading all 36,724 events in ~1.4s. Lookups for one job use
`search()`, which goes straight to it.

## Memory implementation note

**What Priors persists.** Two kinds of thing, written by two processes that
cannot write each other's records.

| Written by | What | Sibyl tier |
|---|---|---|
| Priors | one `decision` per funded job: the probability, the rules that moved it, the block it was decided at | COLD (journal) |
| Resolver | one `episode` per resolved job: outcome, Brier, whether the call was right | COLD (journal) |
| Resolver | `rule` records: condition, delta, status, support, applications, hits | WARM, then ARCHIVE on demotion |
| Resolver | `provider` records: funded/completed counts, last block, last five jobs | WARM |
| Resolver | one `calibration` ledger: observed rate per confidence band | WARM |

**What Priors recalls.** Exactly one function feeds a decision,
`PriorsMemory.recall_experience(provider, client, amount)`. Nothing else in the
codebase reads Sibyl for decision input. It is a keyed read scoped to the
subject of the decision rather than a search, so the whole store is never
loaded and a near-match from the wrong provider cannot come back.

**How it uses them.** The recalled rules are the only memory that moves a
number, with each matching rule contributing a weighted logit shift to the
chain-only baseline, capped so no stack of rules can run away. Calibration is
recalled and reported but never applied, having been measured and rejected. The
provider record supplies the counts the baseline shrinks.

**How you can tell it is memory rather than recomputation.** The journal is
ordered by write time, and the decision for a job is written before its episode
exists, visible in the `show_memory.py` output above, 214 blocks apart.
Deleting the store changes 187 decisions while the code stays the same.

## What is real and what is not

| Claim | Status |
|---|---|
| Predictions written before outcomes exist | **Real, and structurally enforced.** Each block runs in three phases, absorb attributes, predict, absorb outcomes, so a prediction cannot see its own outcome. There is no check to forget to run |
| 187 decisions changed by memory over 18,360 jobs | **Real, and reproducible from a clean clone.** The scan ships with the repo |
| Deletion changes behaviour | **Real.** No `if memory_enabled` branch exists. Stages 2 and 3 have nothing to recall and the prediction falls back to stage 1 |
| 21 jobs on Base mainnet | **Real, and permanent.** Including the one that does not exist |
| Accumulated over months of live trading | **No.** The replay runs in fast forward against a scan of already-recorded history. The live tail is the exception and is labelled wherever it appears |
| An independent counterparty | **No.** `digest/` is an agent I also operate. Both sides of every live job are mine |
| Failures observed in the wild | **No.** Every one was injected through `DIGEST_FAULT_NEXT`, by hand and deterministically |
| The live result measures whether Priors hires better | **No.** It measures whether the decision depends on what was remembered. n = 18, one counterparty, faults on purpose |
| The collection ran through the gate | **No.** It bypassed it, because a gate that stops you transacting also stops you measuring. See the selective labels section |
| The feature set was discovered by the miner | **No.** Individual rules are temporally clean, but the condition vocabulary they choose from was written by someone who had already analysed this dataset. That is a separate limitation from outcome leakage |
| The aggregate improvement is large | **No.** Accuracy moves 0.9000 to 0.9035, and Brier 0.0721 to 0.0666, which is 7.6%. The deleted run is not a chain lookup: it still scans 6,319,153 blocks and shrinks per-provider rates, so it starts at 0.9000. The reversal count is the claim, 187 decisions changed and 126 of them right |

The 18,360-job replay is the part that runs with no hand on it. Everything
involving Digest is a controlled demonstration and is described as one.
