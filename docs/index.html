An agent that predicts before it hires, and remembers when it was wrong.

Priors is a buyer agent on Virtuals Protocol ACP that writes down what it expects to happen before hiring anyone, then reads back what they actually did. What it learns lives in Sibyl Memory, and deleting that memory changes what it does.

Most jobs die in silence

Of 75,340 jobs created only 18,367 were funded, and of the 56,973 that died, 40,161 drew no provider response at all while 16,812 got an answer but never reached funding.

Predicting whether a job completes does nothing about that, so Priors asks first and weighs the answer against its record of the same provider's earlier ones.

Response means one specific thing here: a BudgetSet event, which is the first move a provider makes on a job, before any money is escrowed. The event records the job but not who set the budget, so these are counted as responses and Priors does not claim the provider ignored anyone.

Stage 1

Chain evidence

Per-provider completion rates, shrunk toward the market base rate so a provider with 3 jobs is not read like one with 300. Public data. Works with memory deleted.

Stage 2

Rules from its own errors

Mined from Priors' own resolved mistakes, running pattern to provisional to graduated or demoted, with each rule applying only to jobs funded after the evidence that formed it.

Stage 3

Calibration

Priors' record of how its own confidence has held up. Measured, kept, and deliberately not allowed to move the decision.

156 is the total, and the three states below it are that same 156 split up: 117 + 16 + 23. Every rule is in exactly one of them at the end of the replay, spread across 51 providers.

Nobody can write the record that scores their own claim. Priors writes decisions and requests, the resolver writes episodes and observations, and the counterparty can only declare. That separation is enforced by the API surface itself and pinned by tests.

Both runs scored 0.7947 on whether the job would complete, so the predictor never changed its mind. Only the memory differed.

The bar is not a tuned constant because it is 0.4669, and 0.4669 is the marketplace itself. Only 35,179 of 75,340 created jobs ever drew a provider response, which gave us 0.4669.

A prior is what you believe before you have any evidence, which is where the project gets its name. The marketplace prior is 0.4669: what to expect of a provider you know nothing about. A provider's reliability starts there and is pulled toward whatever its own record shows:

reliability = (kept + 5 × 0.4669) ÷ (observed + 5)

The 5 is a handicap, so it takes five real observations before a record outweighs the marketplace rate and one broken promise is never a verdict. For a provider Priors has never met there is nothing to weigh:

(0 + 5 × 0.4669) ÷ (0 + 5) = 2.3345 ÷ 5 = 0.4669

Exactly the bar. A stranger passes, and the deleted run clears by construction and not by a number picked to let it through.

What memory changed

Both runs are the same code, and the deleted run is never handicapped.

126 right, 61 wrong, and nearly all the same shape: memory overruling a hire the chain record endorsed, on a job that then failed.

Memory removed 64 wrong calls and improved Brier by 7.6%, from 0.0721 to 0.0666, which measures whether the confidence was honest and not only whether the verdict was right. On the 187 decisions it changed outright it was right on 126.

Accuracy moves only 0.9000 to 0.9035, because the run without memory is already strong. That run still scans 6.3 million blocks, decodes every ACP event, builds per-provider counters and shrinks them toward the market rate. It is Priors with stages 2 and 3 removed, not a chain lookup, so nothing you could read off BaseScan comes near it. Against a baseline like that, 1,836 wrong calls remain out of 18,360 and memory takes 64 of them, on a problem where hiring everything already gets 14,597 of 18,367 right.

This table is also only half of it. The 40,161 jobs that draw no response are invisible to a completion score, and on that side deletion moves the number from 0.1666 to 0.4669, which you can run yourself.

What Priors refuses to do

Two things we switched off

Both were wrong on the evidence, so neither is allowed to act, and they are not dead code either because both still run inside scripts/ablation.py, which measures the predictor with each of them switched on, which is what makes a negative result checkable instead of asserted.

Rejected

Calibration as an input

Applying it flipped 458 decisions and was right on 45% of them, worse than a coin. It is a band-wide average applied to individual jobs, and with the hire bar at 0.5 a correct average nudge pushes fine jobs across the line. Kept as self-knowledge, kept out of the call.

Rejected

A learned hire threshold

Built under the same temporal separation as rules. Every bar above 0.5 scored worse against the real outcome distribution. A threshold is not a learnable fact but a policy choice needing a stated cost model, and inventing one that made the numbers work would be fitting to the replay.

Kept

Rules

187 decisions changed, 126 of them right, across 13 providers. Priors changes its behaviour only when its own evidence earns that right.

The journal is the truth

The summary is disposable

Priors stores two things. The journal is append-only: one decision per funded job, one episode per resolved job, never edited. The provider records and rules are a summary, rewritten in place every time something changes. The journal is written first, so if a process dies between the two the record survives and the summary can be rebuilt.

$ python scripts/rebuild_from_journal.py

  journal events read     : 36,724 in 0.4s
  decisions               : 18,367
  episodes                : 18,357

                            from the journal     published
  accuracy                            0.9036        0.9035   match
  Brier                               0.0665        0.0666   match
  decisions                           18,367        18,367   match

Those figures were recomputed from the journal alone. No provider record was read, no rule, no calibration ledger. The summary can be destroyed and nothing published here is lost.

Reproduce it

Run it on your own machine

Nothing to install

Read the chain

Look up jobs 76935, 76936, 76941, 76945, 77933 and 77934 against ACP at 0x238e541b on Base. Sixteen of them carry a JobCreated and nothing else. Nobody can edit it, including this project and Sibyl.

A clone and 30 seconds

Run the tests

58 tests, standard library only, no fixtures and no network. Each pins a claim made on this page, including that the response bar is the marketplace prior and that no writer can reach the record scoring its own claim.

A clone and a few minutes

Delete the memory yourself

The 150 MB scan ships with the repo, gzipped to 15 MB, so the replay regenerates from a clean clone. Run the memory check, then run it again with --empty, and compare the two.

git clone https://github.com/bzdmin/priors-acp && cd priors-acp
pip install sibyl-memory-client

python -m unittest discover -s tests -t .    # 58 tests, no data needed

python scripts/fresh_session.py              # memory intact
python scripts/fresh_session.py --empty      # memory deleted
python scripts/ablation.py                   # with and without each mechanism

All of it reproduces, including the live record. The 18 observations are exported to docs/data/coordination.json and coordination_report.py --from-export replays them, so the number in the panel above regenerates on any machine.
